# Задание: рефакторинг ITD-Studio (архитектура, аналитика, новый дизайн)

Ты — ведущий разработчик. Тебе передают проект **ITD-Studio** — панель аналитики для аккаунта в соцсети «итд» (сайт `xn--d1ah4a.com`, Python-клиент `itdpy`). Автор давно его не трогал, код вырос хаотично. Твоя задача — привести проект в порядок так, чтобы любой новый разработчик за 10 минут понял, где что лежит и за что отвечает каждый файл, исправить неверную аналитику и сверстать новый дизайн по приложенным скриншотам.

Работай поэтапно (этапы ниже). После каждого этапа проект должен запускаться. Не выдумывай данные там, где их нет: если какую-то метрику нельзя получить честно — так и покажи в интерфейсе.

## 1. КРИТИЧНО: аналитика роста аудитории считается неправильно

### Что сломано
`backend/src/services/analytics/growth_service.py::build_followers_growth_series` **не использует реальных данных о подписчиках вообще**. Она берёт текущее `followers_count` и «размазывает» его по дням пропорционально количеству постов в этот день. В итоге график — выдумка: например, на 12.03.2026 показывается 16 подписчиков, хотя реально их было больше. Любой график «роста подписчиков», построенный так, нужно удалить.

### Что есть в API (проверено в `venv/Lib/site-packages/itdpy`)
- `client.users.me()` / `client.users.get(username)` → `followers_count`, `following_count`, `posts_count`, `created_at` (дата регистрации). Только **текущее** значение, истории нет.
- `client.users.get_followers(user_id, limit, page)` → список подписчиков **без даты подписки**.
- `client.notifications.list_all()` → уведомления с `type` (есть `follow`, `follow_request`, `follow_accepted` в `itdpy/enums.py`) и `created_at`. **Это единственный источник реальных дат подписок.** Проверь глубину истории уведомлений на реальном аккаунте и есть ли события отписки.
- `client.posts.get_stats(post_ids)` — проверь, что возвращает (возможно, актуальные метрики постов).

### Что нужно сделать
1. **Снимки (snapshots).** Новая таблица `account_snapshots(id, user_id, captured_at, followers_count, following_count, posts_count)`. При каждой синхронизации записывать снимок. Это даёт честную историю с момента внедрения.
2. **Снимки метрик постов.** Таблица `post_metrics_snapshots(post_id, captured_at, views, likes, comments, reposts)`. Сейчас `INSERT OR REPLACE` перезаписывает метрики, и динамика поста теряется.
3. **Восстановление прошлого.** Из уведомлений типа `follow` построить ряд «новые подписчики по дням» (реальные даты). Сохранять их в таблицу `follow_events(follower_id, followed_at, source)` с дедупликацией. Накопительную кривую строить «назад» от текущего `followers_count`: `followers(t) = current − подписки после t` (+ отписки, если API их отдаёт; если нет — явно пометить, что ряд — оценка без учёта отписок).
4. **В интерфейсе** чётко различать: «реальные данные (снимки)», «восстановлено по уведомлениям», «данных нет». Никаких интерполяций без подписи.
5. Остальные графики «роста» (лайки/комменты/репосты/просмотры) сейчас — накопительная сумма метрик постов **по дате публикации поста**, а не рост во времени. Переименуй их честно («Лайки по постам, опубликованным в этот день») или перестрой на основе `post_metrics_snapshots`.

### Другие баги аналитики (исправить)
- `build_growth_series(..., 'views')`: в `metric_field_map` нет `"views": "views_count"` → график просмотров всегда 0.
- `overview_service.py:63`: если у топ-поста `content = NULL`, `None[:200]` → 500.
- `ITDService.get_user_posts` игнорирует параметр `limit` (захардкожен 5000).
- `posting_time_service`: час берётся из строки ISO без учёта часового пояса. Привести к часовому поясу пользователя (по умолчанию `Europe/Moscow`, сделать настраиваемым) и учитывать, что посты в одном часе могут быть 1 штука — требовать минимум выборки на бакет, а не только 5 постов всего.
- `engagement_rate` делится на сумму просмотров — оставить, но назвать в UI «ER по просмотрам» и показать формулу в подсказке.
- `created_at` хранится строкой — хранить как ISO-8601 UTC, парсить через `datetime`, а не `split("T")`.

Напиши **pytest-тесты** на все функции аналитики с крайними случаями (пустые посты, NULL-поля, разные часовые пояса, один день, разрывы в датах).

## 2. Архитектура бэкенда

Автор просит «микросервисы». Для одного пользователя и одной SQLite настоящие микросервисы (отдельные процессы + сеть + брокер) дадут только накладные расходы. Делай **модульный монолит с чёткими границами модулей**, где каждый модуль можно позже вынести в отдельный сервис без переписывания. Отдельным процессом выдели только **sync-воркер** (фоновая синхронизация), потому что он долгий и ходит во внешний API.

Целевая структура (ориентир, допускаются разумные отклонения — объясни их в README):

```
backend/
├── app/
│   ├── main.py                    только сборка FastAPI: create_app(), middleware, подключение роутеров
│   ├── core/
│   │   ├── config.py              pydantic-settings: DB_URL, CORS_ORIGINS, TIMEZONE, SYNC_COOLDOWN, SECRET_KEY…
│   │   ├── logging.py             настройка логов (без токенов и PII)
│   │   ├── security.py            сессии/JWT, шифрование refresh_token
│   │   └── errors.py              единые исключения + exception handlers (клиенту — общий текст, детали — в лог)
│   ├── db/
│   │   ├── session.py             SQLAlchemy 2.0 engine/session (SQLAlchemy уже в requirements)
│   │   ├── models.py              ORM-модели: User, Post, AccountSnapshot, PostMetricsSnapshot, FollowEvent, SyncJob
│   │   └── migrations/            Alembic; первая миграция должна подхватить существующую data.db без потери данных
│   ├── integrations/itd/
│   │   └── client.py              единственное место, где импортируется itdpy; маппинг в свои DTO
│   ├── modules/
│   │   ├── auth/                  router.py, service.py, schemas.py — вход по refresh_token, выдача своей сессии
│   │   ├── sync/                  router.py (поставить задачу, статус), service.py, worker.py, schemas.py
│   │   ├── users/                 router.py, repository.py, schemas.py
│   │   ├── posts/                 router.py, repository.py, schemas.py
│   │   └── analytics/
│   │       ├── router.py
│   │       ├── schemas.py         Pydantic-модели ответов (никаких голых dict)
│   │       ├── overview.py
│   │       ├── audience.py        рост подписчиков (снимки + follow_events)
│   │       ├── engagement.py
│   │       └── posting_time.py
│   └── api/deps.py                общие зависимости: get_db, get_current_user
├── tests/                         pytest: unit на analytics, интеграционные на роутеры (TestClient)
├── .env.example
├── .gitignore                     venv/, __pycache__/, *.db, .env
├── requirements.txt               только реально используемые пакеты (DrissionPage*, openpyxl, psutil, lxml — проверить и убрать)
└── README.md
```

Правила:
- Роутер → сервис → репозиторий. Роутер не ходит в БД, сервис не знает про HTTP.
- Один файл = одна ответственность. В начале каждого модуля — короткий docstring «за что отвечает».
- Никакого копипаста `try/except` в эндпоинтах — общий exception handler.
- Все ответы — Pydantic-схемы, документированы в OpenAPI (`/docs`).
- Путь к БД — из конфига, абсолютный, не зависящий от текущей директории.
- Удалить мёртвый код: `delete_old_posts` (если не нужен), импорт `tests.test_analytics` в main.

## 3. Безопасность (обязательно в рамках рефакторинга)

1. **refresh_token не должен быть в URL.** Сейчас `POST /api/sync/{refresh_token}` — токен попадает в логи и историю. Новый поток: `POST /api/auth/login` с токеном в JSON-теле → бэкенд проверяет его через `users.me()`, сохраняет **зашифрованным** (Fernet, ключ из `.env`) и выдаёт свою сессию (httpOnly cookie или JWT). Дальше `POST /api/sync` без токена.
2. **Авторизация на всех эндпоинтах.** Пользователь видит только свои данные. Сейчас любой может прочитать `/api/analytics/{любой_username}`. Убрать `username` из путей, брать из сессии (`/api/analytics/overview`).
3. **Rate limit на синхронизацию** на бэкенде (например, не чаще раза в 10 минут на пользователя) — частые синки приводят к вылету из аккаунта «итд».
4. **Синхронизация асинхронная**: `POST /api/sync` создаёт `SyncJob` и сразу возвращает `job_id`; фронт опрашивает `GET /api/sync/{job_id}`. Закрытие клиента itdpy — в `finally`.
5. Валидация параметров: `limit: int = Query(50, ge=1, le=200)`, `offset ge=0`.
6. Не отдавать `str(e)` клиенту. Не логировать токены.
7. CORS — из конфига, только нужные методы/заголовки.
8. Фронт: `window.open(url, "_blank", "noopener,noreferrer")`; исправить опечатку `@${username}}` в `PostsSection.tsx`.

## 5. Новый дизайн

К заданию приложены скриншоты нового дизайна. Требования:
- Сверстай интерфейс максимально близко к скриншотам: сетка, отступы, типографика, цвета, скругления, состояния (hover, загрузка, пусто, ошибка).
- Вынеси все цвета/размеры в дизайн-токены (CSS-переменные) в `shared/theme`. Темы (тёмная/светлая, если есть на макетах) — через токены, без дублирования CSS.
- Компоненты UI — в `shared/ui`, без логики данных.
- Адаптивность: десктоп и мобильная ширина (от 360px), без горизонтального скролла.
- Если на скриншотах есть блоки, для которых нет данных в API (см. раздел 1), — сверстай их с честным пустым состоянием и подписью, почему данных нет, и перечисли такие места в отчёте.
- Если на скриншотах чего-то не видно (например, мобильной версии или состояния ошибки) — реши сам в том же стиле и укажи это в отчёте.
